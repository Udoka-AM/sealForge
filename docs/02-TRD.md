## 2.3 Backend and database

| Service | Tech | Responsibility |
|---|---|---|
| **Coordinator API** (`crates/sealforge-coordinator`) | Rust, **axum 0.8**, tokio, **sqlx** (Postgres) | Auction CRUD + state machine, bid-instruction generation, status endpoints, publishing results, refund scheduling, PCZT signing-session relay |
| **Escrow scanner** (inside coordinator, separate task) | `zcash_client_backend` compact-block scanning with the escrow IVK via Zaino gRPC | Detects incoming notes, parses memos, writes `bids` |
| **Clearing engine / Merkle / denominations** (`crates/sealforge-core`) | Pure Rust, no I/O, WASM-compatible | Deterministic clearing, Merkle tree, receipts, memo codec, refund planner. Shared by coordinator and auditor |
| **Escrow / FROST** (`crates/sealforge-escrow`) | `frost-core` / `reddsa` (RedPallas, rerandomized FROST), PCZT crates, `zcash-devtool` flows | DKG orchestration, building refund/payout PCZTs, aggregating signature shares |
| **Auditor** (`crates/sealforge-auditor`) | Rust lib + CLI (clap), WASM build via `wasm-bindgen` | Rescans the block range with the published IVK and recomputes the result |
| **Database** | **PostgreSQL 16** | Auctions, bids, results, refunds, signing sessions, scanner state. Migrations with `sqlx migrate` |
| **Zcash node** | **Zebra** (`zebrad`) testnet → mainnet | Full validating node |
| **Indexer** | **Zaino** (lightwalletd as fallback) | Compact-block gRPC for the scanner and WebZjs |
| **gRPC-web proxy** | **Envoy** | Exposes Zaino to browsers (WebZjs) |

**Region:** EU (Germany). One VM, Hetzner `CCX23` (4 vCPU, 16 GB RAM, 360 GB NVMe for mainnet; a smaller box is fine for testnet), runs Zebra, Zaino, Envoy, the coordinator and Postgres through `infra/docker-compose.yml`. Vercel serves the frontend from its edge network.

## 2.4 Authentication and roles

Bidders never create accounts. Privacy beats convenience here, and the receipt is the only bidder credential.

| Role | Sign-in method | Permissions |
|---|---|---|
| **Anonymous bidder** | None. Holds a local receipt (commitment + salt) | Read public auction data. Request bid instructions. Read own receipt and inclusion proof (computed client-side) |
| **Organiser** | Ed25519 keypair generated by `sealforge init`. Each API call is signed (`Authorization: SF-Sig keyId=…, ts=…, sig=…`), with a 60 s clock skew window and nonce replay protection | Create/edit `draft` auctions they own, open, close, publish, start refund planning, configure payout UA |
| **Trustee** | Ed25519 keypair registered by the organiser at auction creation. FROST share stays on the trustee's machine | Join DKG, fetch signing packages, submit signature shares for auctions they are trustees of. Can't edit auctions |
| **Auditor (public)** | None | Read published results, IVK, Merkle root, block range. Run the auditor locally |
| **Operator (infra)** | SSH key on the VM. Not an API role | Deploy, backups. No access to FROST shares |

The organiser and trustee keys are distinct from any Zcash spending key. The coordinator never holds a spend-capable key. It holds only the escrow **IVK/UFVK** needed for scanning and PCZT construction.

## 2.6 Architecture

```
                        ┌──────────────────────── Browser ────────────────────────┐
                        │ apps/web (Next.js)                                       │
                        │  • Auction / Bid / Receipt / Verify / Organiser console  │
                        │  • ShieldRamp: wagmi ⇄ EVM, WebZjs ephemeral wallet      │
                        │  • Auditor WASM (sealforge-auditor)                      │
                        └──────┬───────────────┬──────────────────┬───────────────┘
                     HTTPS/JSON│               │ gRPC-web         │ HTTPS (server route)
                               ▼               ▼                  ▼
┌──────────── VM (docker compose) ────────────────────┐   ┌────────────────────┐
│ sealforge-coordinator (axum)                        │   │ NEAR Intents 1Click │
│  ├ REST API  ├ escrow scanner  ├ refund scheduler   │   └────────────────────┘
│  └ signing-session relay                            │
│        │ sqlx                 │ gRPC                │
│        ▼                      ▼                     │
│   PostgreSQL 16          Zaino ◀── Zebra (zebrad)   │
│                            ▲                        │
│                          Envoy (gRPC-web) ◀─────────┼── browsers
└─────────────────────────────────────────────────────┘
         ▲ signed REST (Ed25519)
┌────────┴─────────┐        FROST shares never leave trustee machines
│ sealforge CLI    │ ×3 trustees: DKG rounds, sign PCZT batches
└──────────────────┘
```

**Data flow (core loop):**
1. **Create:** organiser CLI → `POST /auctions` → `draft`. Trustees run the DKG via the coordinator relay (round packages are relayed, secrets stay local) → escrow UFVK registered → `ready`.
2. **Open:** organiser opens → the coordinator exposes `GET /auctions/:id/bid-instructions?amount=` → client builds memo `SF1:<auction_id>:<commitment>:<refund_ua>` + ZIP-321 URI locally (the commitment salt never leaves the browser).
3. **Bid:** the wallet pays the escrow UA. The scanner (IVK) sees the note → decodes memo → `bids` row (`valid` / `invalid` + reason).
4. **Close:** at `close_height` the book freezes → `sealforge-core::clearing` computes winners + price → Merkle root over the sorted leaves → `clearing_results`.
5. **Publish:** IVK, params, block range and root are made public → the audit page and CLI recompute independently.
6. **Refund:** `sealforge-core::refunds` plans denominated notes + delays → scheduler groups due notes into cross-bidder batches → `sealforge-escrow` builds a PCZT → trustees sign (2-of-3) → aggregate → broadcast via Zaino → mark `paid`.
7. **Payout:** after all refunds are confirmed, the escrow is swept to the organiser payout UA with the same 2-of-3 flow. The sweep is everything left (winners' payments, fee buffer, refund dust) minus the ZIP-317 fee, except payments awaiting manual review, which stay in the escrow. The auction then moves to `settled`.

**ShieldRamp flow:** wagmi connects → `/api/shieldramp/quote` (server route proxies 1Click) → score computed client-side → user signs the EVM deposit → 1Click delivers ZEC to the ephemeral WebZjs wallet → WebZjs shields → random 20–90 min delay (state persisted in IndexedDB, resumable) → ephemeral wallet pays bid instructions in denominations.

## 2.7 Security and privacy

| Asset | Sensitivity | Controls |
|---|---|---|
| FROST key shares | Critical | Generated and stored only on trustee machines (encrypted file, passphrase). Never transmitted. Backup is each trustee's responsibility, printed in a recovery sheet |
| Escrow IVK/UFVK | High during auction, public after close | Stored encrypted at rest (`pgcrypto`, key in env `SF_DATA_KEY`). Published intentionally at close |
| Bid memos (refund UA, commitment) | High during auction | Only in Postgres (encrypted columns for `refund_ua`). Never logged |
| Receipt salt | Bidder-only | Generated and kept in the browser. Never sent to the server |
| Ephemeral wallet seed | Critical (user funds) | Generated in the browser, encrypted with a user passphrase (WebCrypto AES-GCM, PBKDF2 600k), stored in IndexedDB, mandatory backup prompt |
| Organiser/trustee API keys | High | Ed25519 signatures. Server stores only public keys. Nonce table blocks replays |
| 1Click JWT | High | Vercel server env only |

**Access controls:** signed requests checked per role and per auction (organiser owns auction, trustee belongs to auction). Postgres reachable only on the compose network. Envoy exposes only the Zaino read and broadcast RPCs. HTTPS everywhere (Caddy in front of the coordinator and Envoy, automatic TLS).

**Privacy rules (enforced in code review and the M5 audit):**
- No transparent hops in bid, refund or payout flows. The scanner ignores transparent receipts.
- A fresh diversified refund UA per bid. The UI never reuses one.
- No PII in memos. The memo grammar is fixed and validated.
- Request logs drop client IPs and query strings on `/bid-instructions` and `/receipts/*`. Log retention is 7 days.
- Refund timing comes from a CSPRNG. Denomination splitting is deterministic and public, so anyone can check it.

**Retention:** after an auction is fully settled and published, bid rows are kept (they are public via the IVK anyway). Encrypted `refund_ua` columns are wiped 30 days after the final refund. Organiser data is kept until the organiser deletes the auction (only for `draft` or 90 days after `settled`).

## 2.8 Performance and reliability targets

| Metric | Target |
|---|---|
| Coordinator API latency | p95 < 300 ms for reads, < 800 ms for writes |
| Bid detection lag | ≤ 2 blocks after confirmation (~50 s at NU7's 25 s blocks) |
| Auditor rescan (browser, WASM) | < 60 s for a 3,500-block range (one day) on a mid-range laptop |
| Auditor rescan (CLI) | < 15 s for the same range |
| Clearing computation | < 1 s for 20,000 bids |
| Page load (auction page) | LCP < 2.0 s on 4G, JS < 200 KB gzipped excluding WebZjs/WASM (lazy-loaded) |
| Uptime during a live auction | 99.5% for coordinator + scanner. Bids are never lost during downtime, because the scanner resumes from `scanner_state.last_height` |
| Backups | Postgres `pg_dump` nightly + WAL archiving to Hetzner Storage Box, 14-day retention. Restore drill once before the mainnet auction |
| Recovery | RTO 2 h, RPO 15 min. Chain state can be rebuilt from Zebra. Auction state can be rebuilt from the chain via the IVK (the auditor path) |

## 2.10 Key technical decisions and tradeoffs

| Decision | Reason | Alternative considered |
|---|---|---|
| **Rust for the coordinator, escrow and auditor** | librustzcash, FROST and PCZT are Rust-native. One `core` crate gives identical clearing in the server, CLI and WASM | TypeScript backend: faster UI iteration, but it would need FFI or re-implementation of Zcash primitives |
| **Deposit-as-bid in MVP; commit-reveal as stretch** | Ships the full loop in 3 weeks. The trustee-visibility caveat is documented | Commit-reveal from day 1: stronger privacy against trustees, but doubles bidder steps and adds reveal-phase failure modes |
| **FROST 2-of-3 with PCZTs** | No single custodian. PCZT is the Zcash-native multi-party signing format | Multisig isn't available for shielded pools. A single organiser key fails the threat model |
| **Publishing the IVK after close (not the full viewing key)** | Reveals incoming notes (amount, memo), which is exactly what the audit needs, and not outgoing refunds | Publishing the UFVK would also reveal refund destinations and weaken refund unlinkability |
| **Canonical denominations + random delays + batching for refunds** | Breaks the amount and timing correlation (ZIP 318 design) | Single exact refunds: simpler, but ~100% linkable |
| **Envoy for gRPC-web** | Required by WebZjs in the browser | Running a light client server-side would defeat the "seed never leaves the browser" property |
| **Self-hosted Zebra + Zaino on one VM** | Control over the NU7 version and no third-party seeing our scan pattern | Public lightwalletd: no setup, but version risk on NU7 and a privacy leak of the scan pattern |
| **Postgres over SQLite** | Concurrent scanner + API + scheduler writers, `pgcrypto` | SQLite: simpler, but single-writer contention |
| **Next.js on Vercel** | Previews per PR, edge caching for public pages, server routes to hide the 1Click JWT | A static SPA + a separate proxy: one more service to run |
| **No bidder accounts** | Accounts would be a linkage point. Receipts are enough | Email/passkey login: better recovery, but a privacy regression |
