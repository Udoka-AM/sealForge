# Security review (task 5.1, PRD AC14)

**Scope:** coordinator, chain worker, CLI, escrow and signer crates, auditor, and the web app as of branch `task/5-quality` (2026-10-15).
**Method:** code reading against the threat model, dependency audits, and attacks tried on the local regtest chain.
**Status:** every AC14 check passes, with fixes below. Open items are listed at the end with owners.

## AC14 checks

| Check | Result | Evidence |
|---|---|---|
| **No transparent hops** in bid, refund or payout flows | Pass | The escrow address has only an Orchard receiver (`sealforge-escrow::address::escrow_address`). Escrow spends are built with an Ironwood-only change strategy (`sealforge-chain::spend`). Refund and payout addresses must have an Orchard receiver (fixed in this review, see F2). The scanner reads only Orchard and Ironwood notes. ShieldRamp's Intents leg is not built yet (task 4.1); PRD Q4 tracks its transparent-leg question |
| **No address reuse** | Pass, with a user-side caveat | One escrow address per auction, derived from a fresh DKG. The bid form asks for "a fresh Unified Address from your wallet, used only for this bid". The app can't enforce that for an address the bidder pastes. The ephemeral-wallet path (task 4.7) will generate one per bid |
| **No PII in memos** | Pass | Bid memo: `SF1:<code>:<commitment>:<refund_ua>`. The commitment is a salted hash. Refund and payout transactions carry no memo. Fee-buffer memo: `SF1FEE:<code>` |
| **No PII in logs or URLs** | Pass | Caddy drops client IPs, and Caddy redacts `Authorization` by default. The coordinator logs method and path only, and paths contain auction codes and batch ids. The console proxy forwards no client IP headers. No commitment, address or amount appears in any URL or query string (`grep` of `apps/web/src`) |
| **Secrets** | Pass | No keys, `.env` files or key shares tracked in git (`git ls-files`, history grep). `SF_DATA_KEY`, `ONECLICK_JWT` and the Postgres password come from the environment. Escrow UFVKs and refund addresses are pgcrypto-encrypted at rest |
| **Dependencies** | Pass after F1 | `cargo audit`: rustls advisories fixed. Allowed warning: `atomic-polyfill` is unmaintained, but it's only active on targets without atomics (via `frost-core → postcard → heapless`). `pnpm audit --prod`: no known vulnerabilities |

## Findings fixed in this review

| # | Severity | Finding | Fix |
|---|---|---|---|
| F1 | Medium | rustls 0.23.45 had four advisories published 2026-10-14 (RUSTSEC-2026-0346..0349) | Updated to 0.23.46 |
| F2 | **High** | A bid memo's refund address was stored unchecked. One bid with a malformed, wrong-network or transparent refund address made every refund batch it joined fail to build, blocking refunds for all bidders. A Sapling-only address would also have crossed pools and revealed the amount | Unusable addresses are dropped at ingest: the bid still counts, and its refund goes to manual review. Refund and payout addresses must have an Orchard receiver. Covered in `scanner_ingest` |
| F3 | High (availability) | Trustees finishing the DKG together deadlocked in Postgres (HTTP 500) | DKG writes lock the auction row first. The concurrent e2e test fails 5 of 5 times without the fix |
| F4 | Medium (availability) | A signer chosen for a batch who goes offline (or loses their nonces) stranded the batch forever | Signing rounds reset after 30 minutes (`signers_selected_at`). The CLI discards nonces from a reset round instead of refusing to recommit |
| F5 | Medium | The web app sent no CSP and no framing protection (connect-src later widened to `https:` so the browser rescan can reach the auditor's chosen lightwallet server; scripts stay same-origin). The console and trustee pages sign with keys stored in the browser, so a framing site could clickjack them | Production CSP: same-origin scripts and WebAssembly only, `frame-ancestors 'none'`, plus `X-Frame-Options: DENY`. Verified that the WASM auditor and the trustee signer still run under it |
| F6 | Low | Escrow wallet files (viewing-key material) were created with default permissions | The wallet directory is created owner-only (0700) |
| F7 | Low | The restore drill passed `SF_DATA_KEY` on the `psql` command line, where `ps` can see it | SQL goes through stdin |
| F8 | Medium | Payments arriving after close were recorded as valid bids with no refund planned | Stored as `late`, refunded in full by a late-refund planner |
| F9 | **High** | Reported privately on 2026-11-17 by @danielgorgonha from @deegalabs. A trustee kept its round 1 nonces until the shares upload succeeded. After a failed upload, the next CLI run (or the browser's 5-second poll) signed again with the same nonces over whatever sighash, alphas and commitments the coordinator returned. A malicious coordinator collecting shares over one nonce set on different messages can solve for the trustee's signing share; with two trustees' shares it spends alone | Nonces are consumed before any share leaves the device: the trustee records the shares and a digest of their inputs (synced to disk), then deletes the nonces, then sends. A retry resends those exact bytes only if the inputs are identical; otherwise it refuses and waits for the round to reset with fresh nonces. CLI and browser. Test: `dkg_e2e` ("a coordinator that loses a share") |
| F10 | **High** | Reported in the same message. Only the coordinator could check that the escrow UA derives from the FROST group key: it sampled `nk` and `rivk` and gave trustees only the UA, and the published UIVK doesn't contain `ak`. A coordinator could show the address of its own single-key wallet and every existing check would pass | The coordinator seals `nk ‖ rivk` to each trustee. Each trustee rebuilds the UA from its own group key, refuses on a mismatch, and otherwise signs an Ed25519 attestation over the UA. `open` requires all three. Trade-off: trustees gain viewing power over the escrow (THREAT-MODEL trust assumption 2). Bidders: the auction page and the result publish each trustee's key and attestation; the page checks them in the browser and blocks the bid form on a mismatch, and `sealforge-audit` checks them plus that the UIVK receives at that address (`--trustee-key` pins keys). Trustees run `trustee check`, and `trustee sign` refuses if the public page shows another address or another key in their slot. Residual: a coordinator serving trustees and bidders different pages, unless bidders compare keys from the trustees' own channels (THREAT-MODEL known limit 2a). Smaller items from the same reviewer are tracked publicly: sealForge #40 and #41, zPass #4. Tests: `dkg_e2e` (tampered `escrow_ua`, swapped trustee key), `escrow::tests`, `escrow_address` |
| F11 | Medium | Reported publicly by @danielgorgonha from @deegalabs (sealForge #40). An open auction could be cancelled while a bid was in the mempool, or mined but not yet scanned. Cancelled escrows aren't scanned and cancelled auctions aren't public, so that bid got no refund and the bidder lost sight of it; an organiser could time this on purpose | Cancelling is allowed only before the auction opens; open auctions run to close and every non-winning bid is refunded. Fee-buffer funding is offered only once open, so it can't be stranded either. Tests: `lifecycle::tests::open_auctions_cannot_be_cancelled`, `api::open_auction_cannot_be_cancelled_while_a_bid_is_unscanned` |
| F12 | Medium (availability) | Reported publicly by @danielgorgonha from @deegalabs (sealForge #41). The payout swept every escrow note in one transaction, and refund batches were capped by outputs, not inputs. ZIP 218 limits Orchard and Ironwood actions to 330 per block, so an escrow with a few hundred notes (one per bid; or padded on purpose with small payments) would produce a transaction that can never be mined, stalling refunds or the payout | No escrow transaction spends more than 100 notes. The payout sweeps the oldest 100 at a time until the escrow is empty; a refund that would need more waits behind a consolidation of the oldest notes into one at the escrow's internal address. Notes under the 5,000 zat marginal fee are never selected. Tests: `spend::tests`, and a regtest run with the limit lowered to 3 notes (docs/evidence/regtest-e2e.md) |
| F13 | **High** | Reported by @danielgorgonha from @deegalabs (review of #39). The escrow check accepted any non-empty trustee list in which every listed entry was signed: one invented trustee, or one key in all three slots, showed as verified. A pinned slot published with no key fell to "unattested" instead of failing. And the page chose between checking an auction and checking a result by looking for an `auction_code` field, so a coordinator could make an open auction read as an old, unsigned result | Verified now requires exactly slots 1–3 (`TRUSTEE_SLOTS`, shared with the coordinator's creation check), a different key in each, and every one signed; anything else is `Failed` with the reason listed. A pinned slot with no key is `WrongKey`. The page calls separate entry points for an auction and a result (`check_escrow_view_json`, `check_escrow_result_json`), so the coordinator's JSON never picks. Tests: `escrow::tests` (`one_invented_trustee_is_not_enough`, `one_key_in_every_slot_fails`, `slots_must_be_exactly_one_to_three`, `a_pinned_slot_without_a_key_fails`, `an_open_auction_dressed_as_a_result_is_still_checked_as_a_view`) |
| F14 | **High** | Reported by @danielgorgonha from @deegalabs (review of #39). Only the bid page checked the trustee signatures, and it blocked only on an outright "failed": if signatures were missing or the check couldn't run, Continue stayed enabled. My bids ("pay from wallet") and the sealed-bid reveal paid the address the coordinator returned at that moment with no check, and the receipt didn't record which address had been checked. A coordinator that swapped the address after open could collect later payments, and reveals carrying the price and salt | Every payment, reveal and QR code gets its address from one gate (`escrowGate`, `useEscrowGate`), which returns it only when the check says verified for exactly the address shown; checking, an error, unattested and failed all block. The receipt stores the checked address (`escrow_ua`, Rust and TypeScript), and later payments and reveals require it to still match; receipts without it can't pay from My bids. Tests: `apps/web/src/lib/escrow-gate.test.ts`; in the browser, a swapped address blocks the bid page and My bids offers no payment |
| F15 | Low | Reported by @danielgorgonha from @deegalabs (review of #39). `trustee sign` treated a 404 from the public auction page, and a missing local record of the attested address, as "nothing to check" and went on signing; the browser signing console didn't check the public page at all | Signing refuses unless the public page is up and shows the attested address with every trustee's signature (`require_public`); `--allow-unattested-escrow` is the trustee's own opt-in for auctions from before attestations, and nothing the coordinator sends turns it on. The browser console runs the same check, with the trustee's own key pinned to its slot, before round 1 and before round 2. Test: `dkg_e2e` (refusals before open and with the record removed) |
| F16 | **High** (D1, first part) | Design gap recorded as D1: trustees signed the coordinator's sighash without seeing the transaction, so a malicious coordinator with two compliant trustees could pay escrow funds anywhere | Trustees now receive the PCZT and, before committing nonces and before signing, run the shared frost-zec co-signer checks (vendored in `sealforge-verify` at c417ced, MIT, all 17 shared tamper cases pass) plus sealForge's batch rules; the sighash and randomizers are taken from the PCZT, never from the coordinator. CLI (`trustee::check_batch`) and browser (`sealforge-signer-wasm::verify_batch`). Not yet: tying each refund note to its bidder's memo, and detecting double payment. Tests: `sealforge-verify` (`plan::tests`, `tamper_vectors`, `escrow_address`); `dkg_e2e`; regtest run in docs/evidence/regtest-e2e.md |

## Key handling (what an attacker gets)

| Asset | Where it lives | If stolen |
|---|---|---|
| Trustee FROST share | Trustee's disk (`key-package.hex`, 0600), or browser memory while `/trustee` is open | One share can't spend. Two can, together with the escrow FVK |
| Escrow UFVK | Coordinator DB, encrypted with `SF_DATA_KEY` | Bids become visible before close (breaks sealing). Can't spend without two shares |
| `SF_DATA_KEY` | Coordinator environment, password manager, offline copy | With a DB dump: UFVKs and refund addresses. **If lost, escrows can't be spent** (see `infra/README.md` §Backups) |
| Organiser key | `~/.sealforge/organiser.key`, or a non-extractable WebCrypto key in IndexedDB | Can create, open, publish and cancel that organiser's auctions. Can't move funds |
| Nonces (FROST round 1) | Trustee disk until round 2, then deleted. Browser memory only | A nonce plus that round's share would reveal the trustee's signing share. Deleted before any share is sent; a failed send is retried with the same bytes, only over the same inputs (F9) |

## Open items

| Item | Why it's open | Owner |
|---|---|---|
| Rate limiting on public endpoints | Not needed on regtest. Add a Caddy rate limit before mainnet | Ops, task 6.2 |
| Strict nonce-based CSP | Next's hydration needs `'unsafe-inline'` without per-request nonces. React escaping is the primary XSS defence, and there are no `dangerouslySetInnerHTML` sinks | Web |
| Coordinator sees bids before close | By design for v1: it holds the UFVK to scan. Commit-reveal mode (task 4.6) removes the amount from the memo | Product |
| Browser trustee: the key share is in JS memory while the page is open | Same trust as the CLI on that machine. Recommend the CLI for large auctions | Docs |
| Trustee keys reach bidders only through the coordinator (F10) | Attestations are checked, but a coordinator that invents trustees or serves split views is caught only by bidders comparing keys with the trustees' own channels. A key directory or trustee-signed announcements would make this routine | Product + web |
| ShieldRamp transparent leg (PRD Q4) | Feature not built (needs 1Click access) | Task 4.1 |
