## Organiser

Status: `Testnet` (CLI and `/console`).

1. Register: `sealforge init --invite <code> --name <name>` creates `~/.sealforge/organiser.key` (owner-only), or load a key in `/console`.
2. Describe the auction in a TOML file (`examples/auction.toml`): mode (`uniform_price` | `first_price`), quantity, reserve, close height, payout UA (Orchard receiver required), three trustee labels. For sealed-reveal, set `bid_mode = "commit_reveal"` and `reveal_close_height ≥ close_height + 144`.
3. `sealforge auction new <file>` prints three one-time trustee invites. Send each over a private channel.
4. After the trustees finish the DKG, `sealforge auction open <CODE>`. The close height must be at least the tip + 144 ([2.2 Lifecycle](/protocol/lifecycle#height-rules)).
5. Optional, once open: `sealforge auction fund-fees <CODE>` prints a ZIP 321 request for a fee buffer (`SF1FEE`). Useful if the auction may end with no winners. An open auction can't be cancelled, so the buffer always comes back with the payout.
6. After close, **you must publish**: `sealforge auction publish <CODE>`. Refunds don't start until you do.
7. The payout (proceeds plus unspent fee buffer plus refund dust, minus fees) goes to your payout UA after the last refund confirms.

Choosing a mode: deposit mode is simpler for bidders (one payment) but the coordinator sees amounts. Sealed-reveal hides prices from the coordinator until the reveal window, at the cost of a second payment per bidder and a longer auction ([2.1 Roles](/protocol/roles)).

## Trustee

Status: `Testnet`. Code: `crates/sealforge-cli/src/trustee.rs`, browser `/trustee/<CODE>` (`crates/sealforge-signer-wasm`).

0. **Once, before your first auction:** `sealforge trustee identity --published-at <URL or handle>` makes your long-term trustee key. Post the line it prints at that place (your website, GitHub profile, X bio) and leave it there. In every auction you join, this key vouches for your key, so bidders can tell you from a stand-in.
1. `sealforge trustee join <invite>` (your long-term key vouches for you automatically; if you joined without one, run `sealforge trustee certify <CODE>` later), then `sealforge trustee dkg <CODE> --wait`. Your key share is written to your disk (owner-only).
2. **Compare the fingerprint** with the other two trustees on a call or in person. If they differ, stop.
3. **Back up:** `sealforge trustee backup <CODE> > backup.txt` prints one string with your key share and the escrow's viewing key. Keep it offline (paper or an encrypted drive), never in chat or email, then `sealforge trustee check-backup <CODE> backup.txt` and delete the file from the machine. With a second trustee's string it can spend the escrow even if the coordinator is gone; `sealforge escrow recover-check <backup> <backup>` drills that.
4. When batches are due, in the browser (`/trustee/<CODE>`): set a lightwallet server you trust under "Lightwallet server for refund checks", then approve each batch; refund batches are refused until you do. The page keeps its record of signed refunds in this browser, so sign each auction from one place. Or with the CLI: `sealforge trustee sign <CODE> --wait --lightwalletd <a lightwallet server you trust>`. The server is how you check refunds yourself: each refund note's bid is read from the chain and must match. Without it, refund batches are refused. You commit; if you're one of the first two, you sign. Before committing or signing, the CLI and the browser page both check that the public auction page is up, lists your key in your slot, and shows the escrow address you attested with every trustee's signature, and refuse otherwise. For an auction from before escrow attestations, the CLI needs `--allow-unattested-escrow`.

What you check when you sign: the CLI and the browser decode the transaction (PCZT) themselves, compute the sighash, and run the shared frost-zec checks plus sealForge's batch rules: every output is owed, refunds go to each bid's own refund address (CLI, with `--lightwalletd`), and payouts only to the payout address ([5 Security, trust assumption 3](/security#trust-assumptions)). Before releasing your share, you and your co-signer also confirm you were shown the same commitments.

**If the coordinator is gone.** Two trustees can still move the funds with their backup strings alone. Agree a destination by voice first, for example a new escrow or an address that will refund the bidders. Then:

1. Trustee A runs `sealforge escrow recover-start --backup a.txt --lightwalletd <server> --to <address>`, and sends the `request.json` it writes to trustee B. It holds no secrets.
2. Trustee B runs `sealforge escrow recover-cosign --backup b.txt --request request.json --to <address>`, types the address themselves, reads the decoded transaction, and runs again with `--approve` to sign. The `reply.json` goes back to A.
3. Trustee A runs `sealforge escrow recover-finish --backup a.txt --reply reply.json --lightwalletd <server>`, which signs, checks and broadcasts.

**CLI or browser.** The browser trustee page holds your key share in JavaScript memory while it's open, the same trust as the CLI on that machine plus the browser's attack surface. Use the CLI for large auctions. Never run more than one trustee on one machine outside test networks: that defeats the threshold.

## Bidder

Status: `Testnet`.

- **Any shielded wallet:** the bid page shows a ZIP 321 QR (escrow UA, amount, memo). Pay it from a wallet that supports ZIP 321 and memos and holds Ironwood or Orchard funds. Use a **fresh refund address** with an Orchard receiver. It becomes readable to everyone after publish.
- **In-browser wallet:** `/wallet` creates a 24-word phrase and a passphrase-encrypted vault in your browser, and gives each bid a fresh refund address ([WALLET-INTEGRATION.md](https://github.com/Udoka-AM/sealForge/blob/main/docs/WALLET-INTEGRATION.md)).
- **Keep the receipt.** It holds your salt, the only copy. In sealed-reveal mode you need it to reveal. Without a reveal, your deposit is refunded as `not_revealed`.
- **Sealed-reveal:** after the bidding close, send the reveal (10,000 zat, `SF1R` memo) before `reveal_close_height`.
- **Check the trustees before you pay.** The escrow card checks every trustee's signature in your browser. Open "Trustee keys": each trustee shows the long-term key that vouches for it and where it's published. Open those places and check the keys match. Treat a trustee with no long-term key, or a place you don't recognise, as unknown: the signatures prove who signed, not that the three trustees are different people.
- **Verify** at `/verify` once the result is published: inclusion, outcome and refund plan, checked in your browser.
- **Refunds** arrive as several canonical notes at different times. Don't move them all out at once ([2.7](/protocol/refunds#known-residuals)).

## Auditor

Status: `Testnet`. See [6 Verification](/verification#audit-any-auction). Use a lightwallet server you choose, not the auction's. To look for bids outside the published range, widen it with `--from` / `--to`.

## Integrator

- **Embed card** (`Tested`, manually): add `<script src="https://<sealforge-site>/embed.js" data-auction="CODE" async></script>`. It renders in a shadow root, sets no cookies, reads only public fields, and opens bidding on the sealForge site in a new tab (`apps/web/public/embed.js`).
- **Card data:** `GET /api/embed/{code}` (`apps/web/src/app/api/embed/[code]/route.ts`), with CORS `*` and a 30 s cache. Fields: `code`, `title`, `network`, `status`, `accepting_bids`, `sealed_reveal`, `mode`, `quantity`, `reserve_zat`, `close_height`, `blocks_left`, `bid_count` (null below 5 bids), `url`, `audit_url`.
- **Your own bid flow:** use `@sealforge/bid` ([8 API](/api-reference#typescript-sdk)) to build commitments, memos and ZIP 321 URIs client-side. Never send the salt to a server.
- **White-labelled audit page:** `Specified`, not built. Today the audit page is served by the sealForge site; anyone can run `sealforge-audit` or embed the WASM auditor themselves.
