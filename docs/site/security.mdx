## Trust assumptions

Stated first, because every guarantee depends on them. Full text: [THREAT-MODEL.md §Trust assumptions](https://github.com/Udoka-AM/sealForge/blob/main/docs/THREAT-MODEL.md#trust-assumptions).

1. **Deposit mode: the coordinator sees bid amounts live.** It holds the UFVK to scan. Trustees hold no viewing key. Use sealed-reveal mode to hide prices from the coordinator until the reveal window. Deposit sizes stay visible.
2. **The coordinator samples `nk` and `rivk` and holds the UFVK** (encrypted with `SF_DATA_KEY`). That is viewing power, not spending power.
   - A database dump plus `SF_DATA_KEY` gives an attacker every escrow's notes in both directions, so sealing breaks for deposit-mode amounts, and refund addresses leak. Funds don't move.
   - Two trustee shares give spend signatures. Building a spend also needs the escrow FVK, which lives only in the coordinator database under `SF_DATA_KEY`.
3. **Trustees check what they sign.** Trustees now receive the PCZT and run the shared frost-zec co-signer checks (`sealforge-verify`) plus sealForge's batch rules before committing and before signing: they compute the sighash themselves, check every spend is the escrow's and every randomizer matches, decrypt every output with the escrow's full viewing key (rebuilt from their own key share and tied to the address they attested), refuse hidden outputs, foreign pools, excess fee, padding and far expiries, and allow only: a consolidation that pays nobody, a payout of one output to the payout address, refunds of standard-size notes within what the published result owes. For refunds, trustees also read every claimed bid from the chain through a lightwallet server they chose and require each note to go to its bid's memo refund address and fit its refund split together with everything they signed before (a durable ledger; with 2-of-3 any two signing pairs share a trustee, so no note is paid twice). The browser trustee page runs the same checks (#54), through a lightwallet server the trustee sets on the page, and keeps its ledger in the browser's IndexedDB. What remains: the trustees trust the published result's refund amounts and the lightwallet server they chose, and the checks still need the external audit before mainnet.
4. **Liveness.** Refunds need the organiser to publish, the coordinator to build, and two trustees to sign. Any of them can delay. Funds stay in the escrow meanwhile.
5. **The published UIVK is permanent.** After publish, every deposit's amount and memo (code, commitment, refund address) and every reveal (price, salt) is readable by anyone, forever. Senders are not, and outgoing refunds are not.

## Threat model summary

| Adversary | Outcome |
|---|---|
| Chain observer during the auction | Sees nothing about bids |
| Chain observer after publish | Sees amounts and refund addresses, not senders |
| Organiser or coordinator publishing a false result | Detected by the chain audit |
| Hiding a bid from the published list | Detected within the audited block range |
| Coordinator, deposit mode | Sees amounts |
| Coordinator, sealed-reveal mode | Sees deposits, not prices, until the reveal window |
| Coordinator building a malicious spend | **Not protected** (assumption 3) |
| One rogue trustee | Can't sign |
| Coordinator during the DKG | Relays only. Signed and sealed packages, agreement check, fingerprint |
| Replay or forgery of API calls | `SF-Sig`, ±60 s, nonce store |
| Refund amount matching at the exit | Mitigated ([2.7](/protocol/refunds)) |
| Source-chain observer (ShieldRamp) | Not built |

Each row's mechanism and enforcing code: [THREAT-MODEL.md](https://github.com/Udoka-AM/sealForge/blob/main/docs/THREAT-MODEL.md#adversaries-and-protections).

## Mainnet gate checklist

This is the canonical list; [10 Roadmap](/roadmap) links here. Each item MUST be done before an auction holds mainnet funds. Per-auction value caps were considered and decided against (#55): the trustee checks, the external review and independent trustees bound what a fault can do, and a cap would only limit the size of sale sealForge can serve.

- [ ] **Trustee-side transaction verification (D1).** Done for the transaction itself: trustees receive the PCZT, compute the sighash, run the shared frost-zec checks and sealForge's batch rules, and refuse otherwise (regtest evidence: every real consolidation, refund and payout checked and signed). Refund notes are tied to their bids on chain and double payment is refused (CLI; regtest evidence). Remaining: the external audit of these checks.
- [x] **Long-term trustee keys required on mainnet** (#67): the coordinator won't open a mainnet auction until all three trustees are certified, and the browser and the auditor fail the escrow check otherwise.
- [ ] **Independent trustees**: three different operators on separate infrastructure, not one operator's machines.
- [ ] **External review** of the escrow signing path (FROST over PCZT α, `apply_signatures`) and the DKG relay.
- [ ] **Rate limiting** on public endpoints (Caddy).
- [ ] **CSP decision**: nonce-based strict CSP, or a recorded acceptance of `'unsafe-inline'`.
- [ ] **FROST ciphersuite from an upstream-published crate**, replacing `reddsa =0.5.2` and the deprecated fixed-α `sign` ([3 upstream risk](/zcash-integration#dependencies-and-upstream-risk)).
- [x] **Clean, reproducible WASM builds (D2)**: every `BUILD.json` with `"source_dirty": false`, reproduced by the CI `wasm` job (#61).
- [ ] **Off-site encrypted backups drilled** on the production host ([evidence/backup-drill.md](https://github.com/Udoka-AM/sealForge/blob/main/docs/evidence/backup-drill.md) lists what isn't drilled yet).
- [ ] **Rescan performance on real blocks** measured for the 3,500-block audit target ([evidence/perf.md](https://github.com/Udoka-AM/sealForge/blob/main/docs/evidence/perf.md)).
- [x] **Expiry handling for broadcast batches (D3).** Expired batches are marked `expired` and rebuilt.
